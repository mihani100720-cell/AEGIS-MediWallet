3. The exact technology choices
Recommended stack for the first version; not every service needs to be built on day one.
1. Frontend: Next.js + React + TypeScript
Purpose: Build the entire patient and doctor web experience.
UI: Tailwind CSS + shadcn/ui.
Forms: React Hook Form + Zod validation.
Charts: Recharts for health trends and timelines.
QR scanning: html5-qrcode or an equivalent maintained browser library.
Why: Reusable components, strong TypeScript support, responsive layouts and straightforward API integration.
Use it for: Medical vault, dashboard, consent screens, family profiles, appointment calendar and chatbot.
2. Backend: FastAPI + Python
Purpose: Central application API and security enforcement.
Validation: Pydantic.
Database access: SQLAlchemy or SQLModel with Alembic migrations.
Authentication: Validate Supabase-issued access tokens on the server.
API documentation: FastAPI's OpenAPI documentation.
Why: Python integrates well with OCR, document processing, embeddings and AI models.
Example API groups: /auth, /records, /family, /doctors, /consent, /qr, /chat, /prescriptions, /appointments, /audit.
3. Database: Supabase + PostgreSQL
Purpose: Store structured health data and application state.
Authentication: Supabase Auth.
Database: PostgreSQL.
Semantic search: pgvector.
Permissions: PostgreSQL Row-Level Security (RLS) as defense-in-depth, alongside backend authorization.
Why: One integrated platform for the database, user authentication and file storage.
Keep large PDFs and images in private object storage; store their metadata and ownership in PostgreSQL.
4. File storage: Supabase Storage
Purpose: Private storage for uploaded PDFs, scans and prescription photographs.
Use private buckets, file-type and size validation, random object keys and server-enforced access.
Deliver files only after authorization, using short-lived signed URLs when appropriate.
Never store sensitive documents in public buckets or expose permanent public links.
If the project later needs larger-scale document processing, you can evaluate another private object-storage provider without redesigning the whole product.
5. AI: one LLM API + retrieval-augmented generation (RAG)
Purpose: Explain medical reports, answer questions about the patient's own history and generate consultation briefs.
Framework: Start with direct API calls and simple Python orchestration; introduce LangChain or LlamaIndex only if it simplifies the workflow.
Embeddings: A suitable embedding model, with vectors stored in pgvector.
Grounding: Retrieve only the relevant, authorised records; cite the document, date and page or passage.
Quality checks: Validate extracted values, flag missing information and prevent unsupported answers from appearing as facts.
Important: The LLM does not get unrestricted access to the whole database. The backend authorizes retrieval before any relevant content is sent to the AI provider.
6. Document processing: PyMuPDF + OpenCV + PaddleOCR
PyMuPDF: Extract text from text-based PDFs and render pages for inspection.
OpenCV: Image cleanup, rotation correction, contrast enhancement and preprocessing.
PaddleOCR: OCR for printed text and suitable scanned documents.
Handwriting: Evaluate TrOCR or a vision-language model against a set of representative handwritten prescriptions.
Output: Store extracted candidates, confidence, source page and user-confirmed values.
Never silently guess an unclear medicine, strength or dose. Show the original image alongside the extracted text.
7. Language and voice: next-intl + evaluated STT/TTS provider
next-intl for full website translations.
A multilingual speech-to-text service for spoken questions.
A text-to-speech service with tested English, Hindi and Telugu voices.
Language preference saved in the user profile.
Test real pronunciation, medical terminology and speech recognition accuracy before selecting a provider.
Keep the website translation system separate from the voice service so you can replace either independently.
8. Authentication and family verification
Base authentication: Supabase Auth with email/phone verification as appropriate.
Stronger sign-in: WebAuthn/passkeys where supported.
OTP: A configured authentication provider; never implement OTP verification as a frontend-only check.
Face verification: A separately evaluated face-verification and liveness solution, with explicit camera permission and a non-biometric fallback.
Family access: Explicit family membership and individual permissions, not one shared family password.
Face matching is an optional verification step, not automatic permission to open every family member's medical records.
9. QR sharing and consent engine
Python qrcode for QR creation.
html5-qrcode or a comparable maintained library for browser scanning.
Random, opaque, short-lived request identifiers.
PostgreSQL tables for access grants, selected records, purpose, expiry and revocation.
Server-side permission checks every time a doctor requests a record.
The QR code must not contain a patient's medical records, permanent access token or reusable secret. A patient approval creates a scoped grant tied to the verified doctor's account.
10. Background jobs and notifications
Start with a managed scheduler or scheduled backend worker.
Add a queue such as Redis-backed jobs only when workload warrants it.
Send appointment reminders and suspicious-access alerts through a configured email/SMS provider.
Enforce expiry in the API/database authorization logic, not only through a scheduled job.
Use retry handling and idempotent jobs to avoid duplicate notifications.
11. Testing, deployment and monitoring
Backend tests: Pytest.
Frontend tests: Vitest and React Testing Library.
End-to-end: Playwright.
Frontend deployment: Vercel or another suitable Next.js host.
Backend deployment: A managed Python application host or container platform.
CI/CD: GitHub Actions.
Monitoring: Error tracking and privacy-conscious application logs.
Test expired and revoked QR grants, cross-patient data access, failed authentication, private file downloads and AI responses with missing source information.

Four database rules you should not compromise on
Every record has an owner. Every query must respect the authenticated user and any explicitly granted family or doctor access.
Consent is a real permission record. A QR scan is not itself permission to read medical data.
Revocation is enforced on the server. Expired or revoked grants must fail on the next protected request.
Audit logs are protected. Users with ordinary permissions must not be able to rewrite or erase their own security history.
For a real healthcare deployment, add a threat model, backup and recovery procedures, retention/deletion policies, vendor security review and appropriate legal/privacy review. A prototype using these technologies is not automatically compliant with any particular healthcare law or standard.

What belongs where?
apps/web/ — all pages, UI, language switching and browser interactions.
services/api/ — the only central place for application business rules and sensitive access decisions.
ai/ — reusable document processing and AI pipelines. The API calls these modules; they do not independently grant access to data.
database/supabase/ — version-controlled schema migrations, access policies, test data and database tests.
packages/contracts/ — shared API contracts so frontend and backend agree on request and response formats.
docs/ — the design decisions and rules Antigravity should follow.
AGENTS.md — project-wide instructions for the coding agent.
Important: Don't duplicate the whole backend inside Next.js API routes. Keep the FastAPI service as the main backend. Use Next.js routes only for specific frontend/BFF needs, if required.

Aegis Care — Agent Instructions
Product
Aegis Care is a patient-controlled health record platform.
Tagline: "Your Health. Your Authority. Your Shield."
The locked scope contains 18 modules: medical record vault, authentication, family face verification with OTP fallback, access alerts, doctor verification, QR sharing, OPD/admission sharing, consent expiry and revocation, offline emergency QR, AI report summaries, prescription OCR, medicine information lookup, personal AI chatbot, multilingual voice assistant, full website translations, appointments, general wellness guidance, and health timeline/consultation brief/audit.
Required architecture
Frontend: Next.js, React, TypeScript, Tailwind CSS.
Backend: Python FastAPI.
Database and authentication: Supabase Auth and PostgreSQL.
Documents: private Supabase Storage.
AI retrieval: embedding model and pgvector where appropriate.
OCR: PyMuPDF, OpenCV, PaddleOCR; evaluate handwriting-specific models separately.
Languages: English, Hindi, Telugu.
Testing: Pytest, frontend unit tests, Playwright end-to-end tests.
Architecture rules
Keep the frontend in apps/web and the main backend in services/api.
Keep reusable AI/document processing in ai/.
Keep SQL migrations and database policies in database/supabase/.
Use versioned API endpoints under /api/v1.
Separate API endpoints, business services, repositories, schemas, models and access policies.
Prefer small, testable modules over giant files.
Do not add new frameworks or providers without explaining why they are needed.
Security rules
Every protected request must authenticate the user and authorize the requested action server-side.
Verify token signatures and claims; never trust a user ID or role sent by the browser.
Enforce record ownership, family permissions, doctor grants, allowed scope, expiry and revocation.
Use private file storage and check permissions before generating access URLs.
Never expose service-role keys, LLM keys, OTP secrets or other private credentials to the frontend.
Do not log medical document content, OTP values, access tokens or face templates.
Face verification requires explicit camera permission, appropriate consent and a fallback. A face match alone must not grant access to all family records.
QR codes must not contain medical records or permanent reusable access tokens.
Revoked or expired access must be denied by the backend, even if the UI is stale.
Keep audit events protected from ordinary user modification.
Use synthetic data in development and demos.
AI and medical safety
Retrieve only data the current user is authorised to access.
Cite source documents and page references when available.
Clearly flag uncertainty, missing values and conflicting information.
Never invent medicine names, doses, diagnoses or patient history.
OCR output is a candidate extraction until reviewed and confirmed.
AI must not automatically change medication, make definitive diagnoses or share records with a doctor.
Do not claim regulatory compliance, clinical validation or verified credentials without evidence.
Engineering rules
Validate all inputs on the server.
Add tests for each feature and especially for access-control failures.
Maintain .env.example with placeholder values only.
Update README.md and relevant docs when architecture changes.
Do not mark a feature complete unless its core flow works and tests pass.
Before adding a dependency, check whether an existing dependency can do the job.
Make small changes, run relevant tests, inspect errors, and report what changed.
Do not replace working files or restructure the entire repository without a clear reason and explicit review.
Development priority
Foundation and authentication.
Medical records and private storage.
Consent-based doctor sharing and audit.
AI summaries and patient-specific retrieval.
Multilingual interface and appointments.
Advanced OCR, voice, face verification and remaining modules.

6. Final rules before you start coding
One source of truth: Supabase/PostgreSQL stores application data; private storage holds the documents.
One central permission layer: FastAPI authorizes access to records, AI retrieval and doctor sharing.
One feature at a time: Build the UI, API, database changes and tests together.
No fake security: Hiding a button, displaying an expiry timer or scanning a QR is not access control.
No fake AI: Clearly label mock responses and demo data until the actual provider and retrieval pipeline work.
No uncontrolled scope growth: Finish the current phase before adding extra libraries or unrelated features.
Test with synthetic patients: Include at least two separate patient accounts and a doctor account so you can demonstrate both permitted and denied access.

Aspect
Specification
Purpose and user
Patients keep every report, prescription, lab result, imaging report and discharge summary in one place.
